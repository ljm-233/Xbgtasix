# 可行性判定与性能实测

分两问：**能不能跑起来**（可行性）和**跑起来有多快**（性能）。能测的测了，
不能测的说清楚为什么不能测。

## 一、性能（本机实测，`tests/t29_perf`）

| 项目 | 实测 | 说明 |
|---|---|---|
| 启动 `XGameRuntimeInitialize`（含读配置） | **0.52 ms** | 只解析 `MicrosoftGame.Config` 的几个字段 |
| 解析全部 461 个导出（`GetProcAddress`） | **0.058 ms** | 人均 0.126 µs；可忽略 |
| 转发一次调用（系统 d3d12 直调） | 9.68 µs | 被转发的函数本身有开销 |
| 转发一次调用（经 `d3d12_xs`） | 9.62 µs | **额外开销 ≈ 0**（差值在噪声内） |
| `XMemAlloc`+`XMemFree` 一次往返 | **1.15 µs** | 对照 `VirtualAlloc`+`Free` 是 1.02 µs → **1.13 倍** |
| XMem 吞吐 | **868,000 次/秒** | 4 KB 分配 |
| 任务队列提交一次 | **0.036 µs** | 手动模式，锁 + 入队 |
| 任务队列派发一次 | **0.024 µs** | 含回调调用 |
| 异步往返（`XAsyncRun` + wait） | **54 µs** | 见下方"修掉的一个真问题" |

### 修掉的一个真问题：异步往返原本是 15.6 ms

第一版基准测出异步往返 **15,624 µs**，比其他项慢三个数量级。原因：

```
XAsyncGetStatus(wait=true) 用 Sleep(1) 轮询
Windows 默认计时器精度 = 15.6 ms → Sleep(1) 实际睡 15.6 ms
```

改成条件变量（完成即唤醒）后：

| | 改前 | 改后 | 提升 |
|---|---|---|---|
| 异步往返 | 15,624 µs | **54 µs** | **287 倍** |

这条不是微优化：真实游戏在加载线程里 `for (;;) { if (XAsyncGetStatus(b, true) == S_OK) break; }`
这种写法，每次等 15.6 ms，几十个异步就是秒级卡顿。

## 二、可行性：分三层看

### 第 1 层：已证明可行（有测试证据）

| 能力 | 证据 | 状态 |
|---|---|---|
| D3D12 渲染管线（root sig → PSO → draw） | `t1` `t2` `t4` `t5` `t6` | ✅ 518 条断言 |
| mesh shader / DXR 1.1 / bindless 98 槽 | `t5` `t6` `t4` | ✅ 两块 GPU 交叉验证 |
| 内存管理（64 KB 页语义） | `t3` 93 条断言 | ✅ |
| 任务队列（含复合队列） | `t20` `t27` | ✅ **家族桩清零** |
| 异步机制 | `t17` `t21` | ✅ 往返 54 µs |
| 包挂载 / chunk / 存档 | `t18` `t19` `t22` `t23` `t24` | ✅ 真目录 + 真读写 |
| 用户 / 能力门 | `t21` | ✅ 真配置驱动 |
| **加载真实游戏侧 DLL** | `t16`，16/16 加载成功 | ✅ 静态核对 0 缺失 |
| 显卡适配 / 显存预算 | `t13` `t14` `t15` | ✅ |
| 语音合成 | `t28` | ⚠️ 枚举/创建真，朗读本机 SKIP（无音频会话） |

### 第 2 层：无法判定（缺 exe）

| 未知 | 为什么现在无法判定 |
|---|---|
| exe 到底导入哪些符号 | 包内唯一缺失文件就是它 |
| 未实现时游戏是"降级"还是"卡死" | 取决于调用点是否检查返回值，只有跑起来才知道 |
| 首帧 / 稳态帧时间 | 需要真实渲染负载与资产 |
| 资产流式加载的实际吞吐 | 需要 exe 的 I/O 层 |

**这一层有一个已经准备好的测量手段**：`XBGTASIX_UNIMPL=log` 会把每个未实现的
调用连同**调用栈**写进日志。exe 到手后第一件事就是跑一遍，得到的缺口清单就是
"可行性问题的全集"，而不是现在这种猜测。

### 第 3 层：已知不可行

| 不可行 | 原因 |
|---|---|
| 走 `XStore` 的购买/授权链路 | 不伪造授权（设计决定） |
| 需要 XBL token 的功能（成就/多人/隐私） | token 由微软服务按用户签发，离线不可能 |
| 主机统一内存/residency 的精确语义 | `ID3D12DeviceX` 在 NDA 内 |
| 离线 TTS 音频字节 | mingw 的 SAPI 头与 MS SDK 格式协商不一致（见 audit 文档） |

## 三、判定结论

**可行性：技术上成立，但未被"跑通"验证。**

支撑这个判断的三个数字：

1. **461 个导出、16/16 真实 DLL 加载成功** —— 说明 ABI 层面能接住别人的二进制
2. **`d3d12_xs` 转发额外开销 ≈ 0** —— 说明"转发层"不会成为性能负担
3. **启动 < 1 ms** —— 说明 shim 自身不会拖慢启动

**风险不在性能，在覆盖率**：146 个桩里，`XStore` 77 个是设计上不做的，
其余 69 个是否被调用、调用了会不会卡死，**只能等 exe**。
